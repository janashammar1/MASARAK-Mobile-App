Jetpack Compose Components & Libraries

Planned Jetpack Compose components and libraries for the future implementation of MASARAK, with clear justification and a dependency/compatibility plan. No production code is required at this milestone.

2. Planned Jetpack Libraries

Core libraries planned for the future MASARAK implementation.

Jetpack Compose

Justification: Will be used to build the MASARAK Android user interface using declarative Kotlin UI.

Material 3

Justification: Provides the ready-made Material components needed for buttons, cards, text fields, navigation, dialogs, and other UI elements.

Navigation Compose

Justification: Will manage navigation between shared screens and the Student, Field Supervisor, and Academic Supervisor flows.

ViewModel

Justification: Will hold screen state and handle user events so UI logic remains separate from the Compose screens in the planned UDF architecture.

Additional libraries such as Room, WorkManager, Retrofit, or Firebase are not committed at this stage. They will only be added later if the implementation requires them.

3. Dependencies & Compatibility

The following dependencies are the main ones expected for the current plan. Exact version numbers will be selected during implementation after checking compatibility with the project setup.

Dependency Purpose Compatibility approach
androidx.compose:compose-bom Keeps Jetpack Compose library versions aligned. Use one BOM version so Compose UI and Material-related libraries remain compatible with each other.
androidx.compose.material3:material3 Provides Material 3 UI components. Use the version managed through the Compose BOM rather than selecting an unrelated version manually.
androidx.navigation:navigation-compose Provides navigation between MASARAK screens. Select a stable version that is compatible with the Android and Compose setup used by the project.
androidx.lifecycle:lifecycle-viewmodel-compose Allows Compose screens to use ViewModels. Use a Lifecycle version compatible with the project SDK and Compose environment.
Dependency versions are not fixed in Milestone 2 because production implementation has not started yet. The versions will be verified together before coding to avoid library conflicts.
